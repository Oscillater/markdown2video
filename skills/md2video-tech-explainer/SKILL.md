# 技术知识讲解

目标：把“读完一篇文章”改为“看懂一个机制”。画面承担解释任务，不是给旁白随便垫一张图。

## 开始前

- 相对链接以本 skill 目录解析。先读 [Plan 契约](../md2video/references/plan.md)；准备执行时读 [运行参考](../md2video/references/runtime.md)，选画面时读 [组件参考](../md2video/references/components.md)。这些公共规则不在本文件重复定义。
- 确认受众、核心问题、是否保留原稿全文、是否需要成片或仅需 Plan。没有来源或用途时只补问影响编排的问题。
- 示例：[缓存讲解 Plan](examples/cache.plan.json)。它可执行但会生成新配音；先复制到任务工作目录，再按用户内容改写，不直接覆盖示例。

## 一、从文章提取一条解释链

1. **钩子**：先给出一个具体疑问、现象或误解，不用“大家好，今天介绍”。
2. **机制**：解释最少的必要概念。每节解决一个问题；不要把原文所有小标题都照搬成章节。
3. **可观察示例**：用步骤、短代码、终端文本或合适图示，让观众看到机制如何发生。
4. **总结**：回扣开场问题，补一句适用边界或常见误区，不复述整段旁白。

一般先尝试 1～3 分钟的密度，但不承诺固定成片时长。一句一个朗读 Segment，优先短句；不能用“字数 × 固定秒数”给 Plan 填时间。用户要求严格时长时，以真实配音和 timeline 迭代。

## 二、让画面与论点对应

| 内容 | 优先演法 | 避免 |
|---|---|---|
| 一组并列概念、操作步骤 | `step_list`，少量短条目逐条出现 | 一屏堆满长段落 |
| 文件内容、配置、短代码 | `code_display` | 把整篇解说放进代码窗口 |
| 命令与输出示例 | `terminal` | 把终端画面当成已实际执行的证据 |
| 概念过渡或暂缺专用图示 | `gen_image` 或用户提供的本地图片 | 把抽象插画当成准确架构图/流程图 |
| 需要精确空间关系的机制 | 先检查已有素材/组件能否表达 | 用 prompt 假装程序化插画理解了具体语义 |

展示文字与朗读文字当前共用 Segment 的 `text`。选短而可读的命令/代码；如果用户要求长代码显示与自然语言旁白独立控制，说明现有模型的限制，不把旁白硬塞进代码面板。

## 三、按视觉连续性切镜

- 一次逐步展开的列表或演示放在同一 Shot，允许包含多个 Segment。
- 逐 Shot 组件在新 Shot 会重新挂载；不要为每句话都切 Shot，却期望列表继续累积。
- 话题、画面手段或推理阶段改变时再切镜。每节先尝试 1～3 个清晰镜头，不把它当硬性数量限制。
- 标题卡单独成场。小节标题可放在组件场，由引擎显示在上层，但不要因此造成画面遮挡。
- 统一使用 Remotion。配图场通常使用 `full_bleed_image_caption_bottom`；组件场的主体排版归组件。
- BGM 只有在用户提供/确认可用素材时才添加；允许无 BGM，不用缺失路径凑格式。

## 四、执行与技术讲解验收

按公共运行流程执行，启用 `--subtitles`。除公共检查外，逐项确认：

- [ ] 开场提出的问题在结尾得到回答，技术表述有依据，未虚构执行结果或性能数字。
- [ ] 每个正文镜头都知道“画面解释什么”，没有不必要的纯字幕空画面。
- [ ] 步骤顺序正确，列表在同一 Shot 中累积，最后一条没有越出画面。
- [ ] 代码/命令没有超长裁切；朗读是否自然需要试听，不能仅凭抽帧宣布合格。
- [ ] 组件已显示同文时字幕让位是正常行为；配图场的旁白仍有字幕。
- [ ] 未把演示文字当成真实命令执行；若需要真正运行命令，另行确认操作范围。

修改 Plan 而不是临时改引擎来掩盖问题。未能表达的视觉诉求、未试听的段落和残留 warning 一并交付。
